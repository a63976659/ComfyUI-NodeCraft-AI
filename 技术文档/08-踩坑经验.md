# 踩坑经验记录

> 本文档记录项目开发中遇到的典型 bug 和解决方案，供后续维护参考。
> 最后更新时间：2026-06-22

---

## 坑 1：JavaScript Temporal Dead Zone（TDZ）导致面板不渲染

**现象**：开发插件面板内容完全不显示，底部版本栏也消失

**原因**：`switchTab(savedTab)` 在 `const refs = {}` 声明之前被调用。switchTab 内部访问 refs 变量，触发 TDZ ReferenceError，后续所有代码中断执行。

**教训**：`const/let` 声明的变量在声明语句之前不可访问（即使在同一作用域内），与 `var` 的 hoisting 行为不同。

**修复**：将 `switchTab()` 调用移到所有 DOM 构建和变量声明完成之后。

---

## 坑 2：Python dict 误作 tuple 解包

**现象**：仓库名验证永远被跳过，任何非法名称都能通过

**原因**：`validate_repo_name()` 返回 `{"valid": bool, "message": str}`，但调用处写成了 `valid, err_msg = validate_repo_name(repo_name)`。对 dict 做序列解包得到的是键名字符串（`"valid"`, `"message"`），永远为 truthy。

**验证**：
```python
>>> d = {"valid": False, "message": "仓库名不能为空"}
>>> a, b = d
>>> a, b
('valid', 'message')   # 得到键名，不是值！
```

**修复**：改为 `name_check = validate_repo_name(repo_name); if not name_check["valid"]: ...`

## 坑 3：设置面板 querySelector 作用域问题

**现象**：GitHub 可见性 radio 获取值始终为 null 或返回错误元素

**原因**：使用 `document.querySelector('input[name="github_visibility"]:checked')` 查询，但设置面板是动态创建的 overlay（挂载在 document.body 或根容器下）。当存在多个相同 name 的 radio 时会匹配到错误元素。

**修复**：改为 `panel.querySelector(...)` 限定查询作用域在当前设置面板内。

---

## 坑 4：标题栏与标签栏 appendChild 顺序

**现象**：标签栏显示在标题栏上方，界面布局主次颠倒

**原因**：flex column 容器中 `appendChild` 的调用顺序决定了子元素的排列顺序。先 append 标签栏后 append 标题栏导致顺序反转。

**修复**：调整 appendChild 顺序，确保标题栏先于标签栏被添加到容器中。

---

## 坑 5：全局元素放在面板内部导致切换时消失

**现象**：版本信息栏/模型状态栏在切换标签页后消失

**原因**：这些元素被放在某个面板（如 panelDevelop）的子元素中，切换 Tab 时该面板 `display:none` 导致其所有子元素一同隐藏。

**修复**：将需要始终可见的元素（版本栏、模型状态栏）提升为 container 的直接子元素，放在所有面板 div 之后，使用 `flex-shrink: 0` 固定位置。

---

## 坑 6：面板背景色不统一

**现象**：新增的"优化插件"和"功能可视化"面板背景色与"开发插件"面板不一致（显示为透明）

**原因**：只有 panelDevelop 在创建时设置了背景色，新面板未设置。

**修复**：给通用 `.nc-panel` 类添加 `background: var(--nca-bg-primary)`，统一所有面板背景。

## 通用经验总结

1. **声明前使用变量**：始终确保 `const/let` 变量在使用前已声明，特别是在异步/事件驱动代码中
2. **函数返回值类型**：调用函数前确认其返回值类型（dict/tuple/list），不要假设
3. **DOM 查询作用域**：动态创建的 UI 组件应使用局部 querySelector 而非全局 document
4. **布局顺序**：flex 容器中子元素的 DOM 顺序即为视觉顺序
5. **全局 vs 局部元素**：始终保持可见的 UI 元素应放在面板容器外部
6. **并发控制**：异步并发操作出现竞争条件时，优先使用 asyncio.Semaphore 而非简单加锁
7. **ES 模块循环依赖**：拆分模块时优先使用回调参数（panelCtx 模式）而非直接导入

## 坑 7：ES Modules 循环依赖问题

**现象**：前端模块化重构后，面板窗口无法正确引用其他模块的函数

**原因**：会话视图管理器.js（主模块）import 插件开发面板.js，同时插件开发面板.js 也需要调用主模块中的状态函数。直接两者相互 import 会导致循环依赖和初始化错误。

**修复**：采用 `panelCtx` 回调对象模式。主模块初始化时，将公共函数/状态打包为一个对象传入子面板，子面板通过回调对象访问，而不是直接 import：

```javascript
// 主模块（会话视图管理器.js）
import { initPluginPanel } from './插件开发面板.js';

const panelCtx = {
    getState: () => currentState,
    sendMessage: sendMessageFn,
    showToast: showToastFn
};

initPluginPanel(container, panelCtx);  // 将回调对象传入

// 子模块（插件开发面板.js）
export function initPluginPanel(container, ctx) {
    // 通过 ctx 访问主模块功能，而不是直接 import
    ctx.sendMessage(...);
}
```

## 坑 8：SearchReplace 工具重复匹配失败

**现象**：使用 SearchReplace 修改文件时报错：“Failed to match original_text”

**原因**：文件中存在结构相似的重复段落，`original_text` 不够唯一。另一种情况：文件内容在上一次操作后发生变化，但 original_text 依然是旧内容。

**修复**：
1. 操作前先用 Read 工具获取最新文件内容
2. `original_text` 必须包含足够多的上下文（至少 3-5 行）确保唯一性
3. 对于大范围修改（>50行），直接使用 Write 工具覆写整个文件更安全

## 坑 9：asyncio.Semaphore 并发控制

**现象**：GitHub 同步时 API 请求过多，触发 GitHub API 限流，大量请求返回 429

**原因**：使用 `asyncio.gather()` 同时发起所有文件的上传请求，无并发数量限制，导致 GitHub API 限流。

**修复**：使用 `asyncio.Semaphore` 限制最大并发数为 5：

```python
semaphore = asyncio.Semaphore(5)

async def upload_file_with_limit(file_path, content):
    async with semaphore:
        return await upload_file(file_path, content)

# 并发执行，但同时最多 5 个
tasks = [upload_file_with_limit(f, c) for f, c in files]
await asyncio.gather(*tasks)
```

**教训**：并发控制首选 Semaphore，它是协程安全的，不需要额外加锁。适合限制外部 API 请求并发度。

## 坑 10：BM25 中文分词 bigram 技巧

**现象**：BM25 检索对中文内容匹配效果很差，搜索中文关键词几乎没有结果

**原因**：BM25 默认按空格分词，中文单词之间没有空格分隔，导致整个句子被视为一个单词而无法匹配。

**修复**：对中文采用 bigram（双字滑动窗口）分词，英文保持空格分词：

```python
def tokenize(text: str) -> list[str]:
    """中文 bigram + 英文空格分词"""
    tokens = []
    i = 0
    while i < len(text):
        char = text[i]
        if '\u4e00' <= char <= '\u9fff':  # 中文字符
            # 生成 bigram
            if i + 1 < len(text) and '\u4e00' <= text[i+1] <= '\u9fff':
                tokens.append(text[i:i+2])
            tokens.append(char)  # 单字也加入
            i += 1
        else:
            # 英文按空格分词
            j = i
            while j < len(text) and text[j] not in ' \t\n':
                j += 1
            if j > i:
                tokens.append(text[i:j].lower())
            i = j + 1 if j < len(text) else j
    return tokens
```

**教训**：中文 NLP 小工具可使用 bigram 当作轻量分词方案，无需引入 jieba 等依赖，小场景下检索效果接近分词库。

## 坑11：Python cryptography 导入容错

**现象**：不同环境中 cryptography 库可能因 Rust 编译二进制(.pyd)与 Python 版本不匹配而导入失败，触发 `ImportError: cannot import name 'check_ansix923_padding' from 'cryptography.hazmat.bindings._rust'`。此错误会导致整个后端模块链断裂，所有路由不注册，前端请求全部 405。

**根因**：`后端/文件读写操作.py` 顶层 `from cryptography.fernet import Fernet` 失败时抛出异常，阻止模块加载。

**解决方案**：
```python
try:
    from cryptography.fernet import Fernet
except (ImportError, Exception) as e:
    Fernet = None
    logging.getLogger("NodeCraftAI.文件读写").warning(
        f"cryptography 模块加载失败，加密配置功能不可用: {e}"
    )
```

配合 `_get_cipher()` / `_encrypt_value()` / `_decrypt_value()` 中增加 `if Fernet is None` 判断，降级为明文读写。

**教训**：
- 关键第三方依赖务必做 try/except 容错，保证核心功能降级可用
- 环境问题（pip 残留、.pyd 锁定）需关闭占用进程后手动清理再重装
- 容错后需在日志中明确警告，方便运维排查

## 坑12：localStorage 键名冲突（RanKing × NCA）

**现象**：NCA 登录面板提示"未检测到 RanKing 凭证"，即使 RanKing 插件已成功登录。

**根因**：NCA 的 `前端/交互与状态.js` 中两处代码无条件执行 `localStorage.removeItem("ComfyCommunity_Token")`：
1. `_设置Token()` 函数（清除时误删）
2. `_获取Token()` 迁移逻辑（读取后误删）

而 RanKing 插件正是用 `ComfyCommunity_Token` 这个键名在 localStorage 中存储持久凭证。

**解决方案**：
- 移除两处 `localStorage.removeItem("ComfyCommunity_Token")`
- NCA 仅通过 `sessionStorage` 管理自己的会话副本
- localStorage 中的 `ComfyCommunity_Token` 由 RanKing 插件全权管理

**教训**：
- 多插件共存时，localStorage/sessionStorage 键名需明确归属
- 迁移逻辑中的"清理旧数据"操作需确认数据所有权
- 第三方插件集成前需明确其存储协议，避免使用通用键名

## 踩坑记录同步机制演进

本节记录踩坑记录集成到云端（魔搭）与 AI 检索体系的遇到的问题与设计演进。

### 需求背景

- `数据/踩坑记录/` 下以 UUID 为文件名保存踩坑记录（包含 `updated_at` ISO 8601 时间戳）
- 需要多设备共享、双向同步、占位不会被重复上传
- 希望 AI 在生成代码时能自动参考踩坑记录避免不同人重复卷入同一个坑

### 问题一：单向上传丢失多设备修改

**现象**：设备 A 上创建/修改了 FAQ 条目，设备 B 看不到。

**原因**：原始同步仅实现了本地 → 云端的单向上传。

**修复**：新增 `pull_from_cloud()` / `_pull_from_cloud_sync()`，使用 HubApi 列出并下载 `踩坑记录/` 下的 JSON，与本地增量合并。同步循环调整为「清理过期墓碑 → 上传脏文件 → 拉取云端」三步。同时提供手动触发端点：

```
POST /ai-coder/cloud/pull   → 手动触发云端拉取
```

### 问题二：多设备并发修改同一条记录导致覆盖

**现象**：设备 A 与设备 B 同时修改同一条 FAQ，只有后上传的那份生效。

**原因**：缺乏冲突检测与合并策略。

**修复**：以 UUID（文件名）为唯一键去重，冲突时比较 `updated_at` ISO 8601 字符串 —— 由于 ISO 8601 格式字典序等价于时间序，可直接字符串比较，保留较新版本。

```python
if local.updated_at < remote.updated_at:
    apply(remote)        # 远端较新
else:
    upload(local)        # 本地较新或同时，以本地为准
```

**教训**：ISO 8601 时间戳的字符串字典序与时间序一致，避免了反复解析 datetime 的开销。

### 问题三：本地删除后云端反倒拉回来

**现象**：本地删除一条 FAQ，下一轮同步拉取又从云端拉回来了。

**原因**：未区分「本地从未拥有该记录」与「本地主动删除」两种语义。

**修复**：采用墓碑（tombstone）机制。删除时不直接移除，而是创建 `{id}.deleted.json` 并上传同步；拉取时若远端存在同名墓碑则不拉取原记录。墓碑 7 天过期后自动清理（避免无限增长）。同时云端侧删除也采用**墓碑预写入**：云端 `删除FAQ()` 先创建 `{id}.deleted.json` 并标记脏同步到 Dataset，再删除原始 .json 文件，确保本地 pull 时能识别云端删除动作（而不是仅看到远端列表少了一项，无法判断是从未存在还是被删除）。

```
本地删除 FAQ → 创建 {id}.deleted.json (墓碑) → 同步上传到云端
云端拉取 → 跳过已有墓碑的 id → 避免复活
墓碑 > 7天 → 本地 + 云端同步清理
```

**教训**：分布式同步中「删除」是状态而非动作，必须用墓碑表达「已删除」以与「未存在」区分。

### 问题四：AI 生成代码跳过已知踩坑

**现象**：踩坑记录被人工记录了，但 AI 仍反复踩同一个坑。

**原因**：检索层只加载了 `知识库/`下的 Markdown，未加载 `数据/踩坑记录/` 下的 JSON。

**修复**：BM25 索引扩展加载 `数据/踩坑记录/*.json`，doc_id 以 `faq://` 为前缀。检索结果按前缀**分离**返回：KB(top-3) + FAQ(top-2)，后端在提示词中用「参考知识」和「历史踩坑」两个标签插入，使模型能辨别权威性与经验性。

```
BM25 索引加载资源：
  ├─ 知识库/{TAB_FOLDER_MAP[tab]}/**/*.md   → doc_id 以文件路径
  └─ 数据/踩坑记录/*.json     → doc_id 以 "faq://" 前缀（visualize Tab 不加载）
```

**教训**：让 AI 资产「学习」踩坑记录的最低成本路径是复用现有检索体系（BM25），只需添加一种新的文档源与前缀区分机制。

### 问题五：不同 UUID 但同标题的重复条目

**现象**：多设备各自创建标题相同的 FAQ（例如两个人同时记录同一个坑），UUID 不同但内容重复，同步后本地出现两条几乎一样的记录。

**原因**：UUID 去重仅能识别同一文件名的重复，无法发现内容级重复。

**修复**：`_pull_from_cloud_sync()` 拉取前先构建本地 title 索引，远端新条目若 title 与本地任一条目重复则跳过，返回值新增 `duplicates` 统计字段。

```python
local_titles = {entry.title: entry.id for entry in _list_all_faqs()}
for remote in remote_entries:
    if remote.id not in local_ids and remote.title in local_titles:
        duplicates += 1   # 跳过内容重复的远端条目
        continue
    ...
```

**教训**：分布式同步中 UUID 仅保证唯一性，不代表内容唯一性；需要业务主键（如 title）去重以避免语义重复。

### 问题六：FAQ 创建者信息丢失

**现象**：多人协作场景下无法追溯 FAQ 是谁创建的，难以召集作者补充信息。

**原因**：`FaqEntry` 模型原本只记录 `created_at` / `updated_at`，未保存创建者账号。

**修复**：`FaqEntry` 新增 `author: str` 字段，创建时从请求中取 JWT 的 `sub` 作为用户标识，未登录为 `"anonymous"`；更新接口不调整 `author`，保留原作者不变。

```python
author = request.get('user', {}).get('sub', 'anonymous')
```

**教训**：多设备 / 多用户场景下，资产所有者信息应在数据模型初期就预留，以免后续补充需要数据迁移。

### 问题七：知识库双向同步被本地环境污染

**现象**：某设备本地误删或修改了知识库 Markdown 后，同步将该变动上传云端，导致其他设备拉取后知识库被损坏。

**原因**：知识库原采用哈希对比的双向同步，本地任何修改（包括误操作）都会反哺到云端，作为 AI 检索资产的知识库需要更高的可信度。

**修复**：知识库同步改为 **云端 → 本地单向**，以云端 Dataset 为唯一权威源：云端有本地无 → 下载；本地有云端无 → 保留本地不上传；哈希不同 → 始终取云端版本覆盖本地。`_上传本地文件()` 函数保留但不再调用。

**教训**：不同资产应采用不同同步策略——踩坑记录属于多人众包贡献需要双向同步，知识库属于权威发布资产需要单向下发；不要为所有业务采用同一种同步模式。

## 坑 13：文件夹选择器“已选择”标签在刷新/切换会话时不同步

**现象**：文件夹选择器组件显示“已选择: xxx”的标签，刷新插件列表后标签消失，或切换到无 `plugin_folder` 字段的会话后标签仍显示上一次的选择。

**根因**：原本选中状态散落在各面板 `onSelect` 回调中直接操作 DOM（`label.textContent = ‘已选择: ’ + name`），未统一走事件总线。当刷新按钮重建列表时、切换到无插件的会话时，这些散落的 DOM 操作完全被绕过。

**解决方案**：统一通过事件总线 `插件选择变更` 事件同步标签状态。`设置插件文件夹(name)` 为唯一广播入口，刷新按钮、切换会话、手动选择均走同一事件链路：

```javascript
// 层 1：所有选中操作均调用设置插件文件夹()
// 手动选择：onSelect 回调 → 设置插件文件夹(name)
// 切换会话：加载已保存的 plugin_folder → 设置插件文件夹(name)
// 刷新按钮：重建列表后调用 设置插件文件夹(当前已选实例)

// 层 2：设置插件文件夹() emit 事件总线
function 设置插件文件夹(name) {
    当前插件文件夹 = name;
    eventBus.emit('插件选择变更', name);
}

// 层 3：各消费者订阅 插件选择变更 → 更新 UI
// 文件夹选择器: 更新列表选中状态 + 已选择标签
// 优化面板、可视化面板: 更新各自的项目信息栏标签
```

删除各面板中散落的 DOM 直接操作（如 `label.textContent = ...`），改为订阅事件总线。改动文件：`文件夹选择器.js`、`交互与状态.js`、`优化面板.js`、`可视化面板.js`。

**教训**：UI 状态同步应有唯一数据源（Single Source of Truth）。散落的 DOM 操作极易在新增场景时遗漏更新；任何应该全局一致的 UI 状态，应通过事件总线广播并由各消费者订阅更新，而不是就地直接写 DOM。

## 坑 14：CSRF 中间件拦截预认证端点导致登录 405

**现象**：启用 CSRF 保护后，前端调用登录/注册接口返回 `验证失败 (405)` 或 `CSRF token missing or invalid`

**原因**：CSRF 中间件对所有 POST/PUT/DELETE/PATCH 请求强制校验 Token，但登录（/login）、注册（/register）、验证（/verify-login）、刷新令牌（/refresh）等预认证端点，用户此时尚未持有会话和 CSRF Token，必然校验失败。

**修复**：
1. 将预认证端点显式加入 CSRF 豁免列表
2. 采用环境分级策略：本地 ComfyUI 环境完全禁用 CSRF（通过 `是否云端环境()` 判断），魔搭创空间等云端环境保持启用

**教训**：添加全局安全中间件时，必须同步梳理所有"用户未登录即需访问"的端点，逐一配置豁免。

## 坑 15：消息编辑重生成后续记录未正确覆盖

**现象**：像 DeepSeek 网页对话那样从任意已发送消息位置编辑重新生成，期望覆盖后续记录，但实际可能出现历史消息未截断或截断后持久化不一致

**原因**：
1. 后端 `truncate_at` 参数实现需精确定位消息索引，索引计算偏差会导致多截或少截
2. 前端虚拟滚动列表在消息数组突变（截断+追加新消息）时需要正确触发重渲染
3. 截断操作必须先持久化（写入 JSON 文件）再返回响应，否则刷新后状态不一致

**修复**：
1. 后端 `truncate_at` 基于消息 ID 而非数组下标定位，避免并发写入时索引漂移
2. 前端截断后整体替换消息数组引用（而非 splice），确保响应式更新
3. 持久化操作采用同步写入 → 返回成功 → 前端发起重生成的严格顺序

**教训**：涉及历史记录截断的操作，必须保证“持久化先于响应”原则，且前端数组变更需触发完整的 UI 刷新周期。

## 坑 16：工具调用循环上限过低导致任务无法完成

**现象**：API 模型显示“[插示] 工具调用循环达到上限（5 轮）”，模型花了大部分轮次读文件，没有剩余轮次执行写入。

**原因**：`智能体/API模型客户端.py` 中硬编码 `最大工具循环次数 = 5`，对于需要先探索（读文件树、读多个文件）再修改的复杂任务不够用。

**解决**：
1. 提升到 15 轮：`最大工具循环次数 = 15`
2. 提示信息改为动态变量：`f"...（{最大工具循环次数} 轮）"`（避免提示和上限不一致）
3. 位置：`智能体/API模型客户端.py` 第 156 行（非流式）和第 348 行（流式）

**教训**：工具调用循环上限应考虑实际任务复杂度，模型需要先探索后再操作的场景最少需要 8~10 轮；硬编码数字应改为命名变量，提示信息应动态引用该变量。

## 坑 17：i18n key 原始文本显示（缺失翻译条目）

**现象**：优化面板显示 `session.search_placeholder`、`session.default_optimize` 等原始 key 字符串而非对应翻译文本。

**原因**：`前端/i18n.js` 中 zh-CN 和 en 均缺少对应条目，`t('session.search_placeholder')` 回退到返回 key 居名行为。

**解决**：在 `前端/i18n.js` 中补充缺失的 zh-CN 和 en 翻译 key，包括同时新增的会话列表面板公共组件所需的所有 key。

**教训**：新增公共组件时，负责同步平袋添加所有 i18n key，避免现上线后内容又回退到权宜名的错误。

## 坑 18：文件夹选择冲突影响智能体操作

**现象**：插件列表选了 A，但当前会话关联的文件夹是 B，两者不一致导致智能体不知道操作哪个文件夹，外加当前文件夹显示“无”。

**原因**：插件列表选择和会话关联文件夹两个来源无优先级/互斥机制，同时存在导致界面显示“无”而实际还有隐性选中。

**解决**：实现互斥选择逻辑，以最后一次操作为准：
- 选中插件列表 → `最后文件夹来源 = 'plugin'`，清除会话选中
- 切换到带 `plugin_folder` 的会话 → `最后文件夹来源 = 'session'`，清除插件列表选中
- 状态栏永远显示最终生效来源的文件夹

**教训**：当界面存在多个来源可干扰同一个语义状态时，必须明确定义优先级/互斥策略并用状态追踪变量记录“最后有效输入”，避免隐性冲突导致 AI 上下文混乱。
