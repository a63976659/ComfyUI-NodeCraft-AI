# 可视化方法论

## 概述

本文档阐述 ComfyUI 插件功能可视化的设计方法论，涵盖可视化设计原则、3D 力导向图配置、插件架构与功能模块的可视化策略，以及与 NodeCraft AI 可视化引擎的集成方式。

---

## 一、可视化设计原则

### 1.1 信息层级

可视化应遵循"三级信息层级"原则，让用户在不同深度理解插件结构：

| 层级 | 内容 | 视觉表达 |
|------|------|---------|
| **宏观** | 插件整体架构、模块划分 | 节点聚类、颜色分组 |
| **中观** | 模块间依赖关系、数据流向 | 连线方向、粗细、颜色 |
| **微观** | 单个文件/函数的详细信息 | 悬停提示、点击展开详情 |

设计要点：
- 默认视图展示宏观层级，避免信息过载
- 通过交互（悬停、点击）逐层揭示细节
- 节点大小编码重要性：入口文件 > 目录 > 普通文件

### 1.2 颜色语义

颜色应具有一致的语义含义，NodeCraft AI 可视化引擎采用以下色彩体系：

```javascript
// 节点颜色映射（按文件类型）
const NODE_COLORS = {
    python:     '#38bdf8',   // 蓝色 — Python 源文件
    javascript: '#fbbf24',   // 黄色 — JavaScript 前端文件
    config:     '#a78bfa',   // 紫色 — 配置文件（.json/.yaml/.toml）
    directory:  '#6b7280',   // 灰色 — 目录节点
    entry:      '#00ffc8',   // 青色（发光）— 入口文件（__init__.py 等）
    other:      '#94a3b8'    // 浅灰 — 其他类型文件
};

// 连线颜色映射（按依赖状态）
const LINK_COLORS = {
    normal: '#10b981',   // 绿色 — 正常依赖
    error:  '#ef4444',   // 红色 — 导入失败/循环依赖
    weak:   '#6b7280'    // 灰色 — 弱依赖（如动态导入）
};
```

颜色设计原则：
- **冷暖分离**：源代码用暖色（黄），基础设施用冷色（蓝/灰）
- **警示色独占**：红色仅用于错误状态，不可用于普通节点
- **入口高亮**：入口文件使用发光青色，与所有其他类型区分
- **色盲友好**：避免仅依赖红绿区分，同时使用形状/大小编码

### 1.3 交互反馈

| 交互 | 行为 | 实现方式 |
|------|------|---------|
| 悬停 | 显示节点详情（名称、大小、类型） | `nodeLabel` 回调 |
| 点击 | 聚焦节点、高亮关联连线 | `onNodeClick` 回调 |
| 拖拽 | 重新布局节点位置 | 3d-force-graph 内置 |
| 滚轮 | 缩放视图 | 3d-force-graph 内置 |
| 右键拖拽 | 旋转 3D 视角 | 3d-force-graph 内置 |

交互设计原则：
- 悬停反馈延迟不超过 100ms
- 点击操作应有明显的视觉状态变化（高亮、缩放）
- 避免在交互中触发网络请求，所有数据预加载

## 二、3D 力导向图配置

### 2.1 节点样式

NodeCraft AI 可视化引擎基于 [3d-force-graph](https://github.com/vasturiano/3d-force-graph) 库（v1.73.4），通过 Three.js 渲染 3D 力导向图。

节点视觉属性通过以下参数控制：

```javascript
// 节点配置
graph
    .nodeColor(node => NODE_COLORS[node.type] || NODE_COLORS.other)
    .nodeVal(node => {
        // 节点大小编码：目录 > 入口 > 普通文件
        if (node.type === 'directory') return 8;
        if (node.type === 'entry') return 5;
        return 3;
    })
    .nodeLabel(node => `${node.name}\n${formatSize(node.size)}`)
    .nodeOpacity(0.9);
```

节点数据结构：
```javascript
{
    id: "string",        // 唯一标识（通常为文件相对路径）
    name: "string",      // 显示名称（文件名或目录名）
    type: "python" | "javascript" | "config" | "directory" | "entry" | "other",
    size: number,        // 文件大小（字节），目录为 0
    path: "string"       // 相对路径（可选，用于点击跳转）
}
```

### 2.2 边样式

```javascript
// 连线配置
graph
    .linkColor(link => LINK_COLORS[link.status] || LINK_COLORS.normal)
    .linkWidth(link => link.status === 'error' ? 2.5 : 1)
    .linkOpacity(0.6)
    .linkDirectionalParticles(link => link.status === 'error' ? 4 : 0)
    .linkDirectionalParticleColor(() => '#ef4444')
    .linkDirectionalParticleWidth(2);
```

连线数据结构：
```javascript
{
    source: "node_id",   // 起始节点 ID
    target: "node_id",   // 目标节点 ID
    status: "normal" | "error" | "weak",
    label: "string"      // 依赖类型描述（可选，如 "import"、"from...import"）
}
```

设计要点：
- 错误依赖使用粒子动画吸引注意力
- 正常依赖使用细线，避免视觉噪声
- 连线透明度 0.6，确保不遮挡节点

### 2.3 物理引擎参数

力导向布局的核心是物理引擎参数调优。NodeCraft AI 采用以下配置：

```javascript
graph
    .d3Force('charge', null)     // 先清除默认值
    .d3Force('charge').strength(-120)  // 斥力强度
    .warmupTicks(50)              // 预热迭代次数（不渲染，仅计算布局）
    .cooldownTicks(100);          // 冷却迭代次数（渲染并逐步稳定）
```

参数调优指南：

| 参数 | 作用 | 推荐值 | 调整策略 |
|------|------|--------|---------|
| `charge.strength` | 节点间斥力 | -120 | 节点多时增大绝对值（如 -200），节点少时减小（如 -60） |
| `warmupTicks` | 预热迭代 | 50 | 节点多时增大（如 100），减少初始抖动 |
| `cooldownTicks` | 冷却迭代 | 100 | 影响布局稳定速度，值越大越稳定但等待越久 |
| `linkDistance` | 连线长度 | 默认 30 | 层级深的图可增大（如 60），使层次更清晰 |

```javascript
// 大型插件（50+ 节点）的推荐配置
graph
    .d3Force('charge').strength(-200)
    .d3Force('link').distance(50)
    .warmupTicks(100)
    .cooldownTicks(150);
```

### 2.4 相机控制

3D 力导向图默认支持鼠标交互控制相机：

| 操作 | 效果 |
|------|------|
| 左键拖拽 | 平移视角 |
| 右键拖拽 | 旋转 3D 视角 |
| 滚轮 | 缩放 |
| 双击节点 | 聚焦到该节点 |

可通过 `cameraPosition` API 编程控制：
```javascript
// 聚焦到特定节点
graph.cameraPosition(
    { x: node.x, y: node.y, z: node.z + 200 },  // 相机位置
    { x: node.x, y: node.y, z: node.z },          // 焦点
    1000  // 动画时长（ms）
);
```

## 三、插件架构可视化

### 3.1 从 import 依赖图到可视化

文件模式分析将插件的 import 关系转化为可视化的依赖图。流程如下：

```
插件目录
    │
    ▼
[AST 解析] 遍历所有 .py 文件
    │  提取 import 语句
    │  ast.Import → 模块名
    │  ast.ImportFrom → 模块名 + 导入名
    ▼
[依赖映射] 将模块名映射到实际文件路径
    │  "from .图像处理 import ..." → 逻辑处理模块/图像处理.py
    │  "import torch" → 外部依赖（不纳入图）
    ▼
[图构建] 生成 nodes + links
    │  每个文件 → 一个节点
    │  每个 import → 一条有向边
    ▼
[可视化渲染] 3D 力导向图
```

### 3.2 节点分类策略

通过分析文件路径和内容自动分类节点：

```python
def classify_node(file_path: str, file_content: str) -> str:
    """根据文件路径和内容判断节点类型"""
    from pathlib import Path
    p = Path(file_path)

    # 入口文件
    if p.name == "__init__.py":
        return "entry"

    # 目录
    if p.is_dir():
        return "directory"

    # 按扩展名分类
    ext = p.suffix.lower()
    if ext == ".py":
        return "python"
    elif ext in (".js", ".mjs"):
        return "javascript"
    elif ext in (".json", ".yaml", ".yml", ".toml", ".ini", ".cfg"):
        return "config"
    else:
        return "other"
```

### 3.3 依赖关系提取

```python
import ast

def extract_imports(source: str, file_path: str) -> list[dict]:
    """从 Python 源码中提取 import 依赖"""
    dependencies = []
    try:
        tree = ast.parse(source)
    except SyntaxError:
        return dependencies

    for node in ast.walk(tree):
        if isinstance(node, ast.Import):
            for alias in node.names:
                dependencies.append({
                    "source": file_path,
                    "target_module": alias.name,
                    "import_type": "import",
                    "lineno": node.lineno
                })
        elif isinstance(node, ast.ImportFrom):
            module = node.module or ""
            # 相对导入（from . import xxx）
            if node.level > 0:
                module = "." * node.level + module
            for alias in node.names:
                dependencies.append({
                    "source": file_path,
                    "target_module": module,
                    "import_name": alias.name,
                    "import_type": "from",
                    "lineno": node.lineno
                })

    return dependencies
```

### 3.4 可视化优化策略

**问题**：大型插件的依赖图可能过于密集，难以阅读。

**解决方案**：

1. **聚类折叠**：将同一目录下的节点聚类为一个"目录节点"，点击后展开
```javascript
// 构建聚类节点
function clusterNodes(nodes) {
    const clusters = {};
    nodes.forEach(node => {
        const dir = node.path.split('/')[0] || 'root';
        if (!clusters[dir]) {
            clusters[dir] = { id: dir, name: dir, type: 'directory', children: [] };
        }
        clusters[dir].children.push(node);
    });
    return Object.values(clusters);
}
```

2. **外部依赖过滤**：仅显示插件内部依赖，隐藏 torch/numpy 等外部库
3. **循环依赖高亮**：检测并标记循环依赖，使用红色粒子动画
4. **层级布局**：按目录深度分配 Z 轴位置，使层次结构更清晰

## 四、功能模块图设计

### 4.1 从 AST 提取功能模块

功能模式分析与文件模式不同：它不展示文件级依赖，而是提取代码的功能语义结构。

**Python 文件摘要提取**（使用 AST）：

```python
def summarize_python_file(source: str) -> str:
    """提取 Python 文件的类/方法/函数签名"""
    lines = []
    tree = ast.parse(source)

    for node in tree.body:
        if isinstance(node, ast.ClassDef):
            lines.append(f"class {node.name}:")
            for child in node.body:
                if isinstance(child, (ast.FunctionDef, ast.AsyncFunctionDef)):
                    args = ", ".join(a.arg for a in child.args.args)
                    prefix = "async def" if isinstance(child, ast.AsyncFunctionDef) else "def"
                    lines.append(f"    {prefix} {child.name}({args})")
        elif isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            args = ", ".join(a.arg for a in node.args.args)
            prefix = "async def" if isinstance(node, ast.AsyncFunctionDef) else "def"
            lines.append(f"{prefix} {node.name}({args})")

    return "\n".join(lines)
```

**JavaScript 文件摘要提取**（使用正则）：

```python
import re

JS_PATTERNS = [
    re.compile(r'export\s+(?:default\s+)?class\s+(\w+)'),
    re.compile(r'export\s+(?:default\s+)?(?:async\s+)?function\s+(\w+)\s*\(([^)]*)\)'),
    re.compile(r'export\s+(?:const|let|var)\s+(\w+)\s*='),
]

def summarize_js_file(source: str) -> str:
    found = []
    for pattern in JS_PATTERNS:
        for m in pattern.finditer(source):
            found.append(m.group(0))
    return "\n".join(found)
```

### 4.2 AI 语义分析生成功能模块图

功能模式将代码摘要发送给 AI 模型，由 AI 识别功能模块并生成结构化的模块关系图：

```
代码摘要（文件树 + 类/函数签名）
    │
    ▼
[Prompt 构造] "分析以下代码，提取功能模块及其依赖关系，
               以 JSON 格式返回 {nodes: [...], links: [...]}"
    ▼
[AI 模型调用] LLM 分析代码语义
    │  识别功能模块（如"图像处理"、"模型加载"、"UI交互"）
    │  推断模块间依赖关系
    ▼
[JSON 解析] 解析 AI 返回的图数据
    │  容错处理：JSON 修复、字段校验
    ▼
[持久化] 保存到 可视化/功能模式.json
```

功能模块图的节点类型不同于文件模式：

```javascript
// 功能模式节点类型
{
    id: "module_id",
    name: "图像处理模块",
    type: "module",         // 功能模块
    description: "负责图像加载、变换和输出",
    files: ["图像处理.py", "滤镜效果.py"],  // 包含的文件
    functions: ["load_image", "apply_filter", "save_output"]
}
```

### 4.3 双模式对比

| 维度 | 文件模式 | 功能模式 |
|------|---------|---------|
| 分析方法 | AST 静态解析 | AI 语义分析 |
| 节点粒度 | 文件级 | 功能模块级 |
| 边含义 | import 依赖 | 功能依赖 |
| 准确性 | 精确（基于代码） | 启发式（基于 AI 理解） |
| 耗时 | 快（毫秒级） | 慢（需调用 AI 模型） |
| 适用场景 | 调试导入错误、理解文件结构 | 理解功能架构、代码审查 |

## 五、与 NodeCraft AI 可视化引擎集成

### 5.1 后端 API

NodeCraft AI 提供两个 API 端点用于可视化：

| 方法 | 路径 | 功能 |
|------|------|------|
| GET | `/ai-coder/visualization/load` | 加载已保存的分析结果 |
| POST | `/ai-coder/visualization/analyze` | 执行分析并保存结果 |

**加载已保存结果**：
```javascript
const response = await fetch('/ai-coder/visualization/load', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
        plugin_path: '/path/to/plugin',
        mode: 'file'  // 或 'function'
    })
});
const graphData = await response.json();
// graphData = { nodes: [...], links: [...], stats: {...} }
```

**执行分析**：
```javascript
const response = await fetch('/ai-coder/visualization/analyze', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
        plugin_path: '/path/to/plugin',
        mode: 'file'  // 或 'function'
    })
});
const result = await response.json();
// result = { graphData: { nodes, links, stats }, meta: {...} }
```

### 5.2 前端渲染

可视化引擎前端模块（`前端/可视化引擎.js`）提供以下导出函数：

```javascript
import { 加载可视化库, 创建可视化图, 更新图数据, 销毁图 } from './可视化引擎.js';

// 1. 异步加载 3d-force-graph 库（CDN 按需加载）
await 加载可视化库(() => {
    console.log('正在加载可视化库...');
});

// 2. 创建图实例
const graph = 创建可视化图(
    document.getElementById('graph-container'),
    graphData,  // { nodes: [...], links: [...] }
    {
        onNodeClick: (node) => {
            console.log('点击节点:', node.name);
        },
        onNodeHover: (node) => {
            // 更新鼠标样式
            document.body.style.cursor = node ? 'pointer' : 'default';
        }
    }

// 3. 更新图数据（切换模式时）
更新图数据(graph, newGraphData);

// 4. 销毁图实例（面板切换时释放资源）
销毁图(graph);
```

### 5.3 数据持久化

分析结果持久化到插件目录的 `可视化/` 文件夹：

```
<plugin_path>/
└── 可视化/
    ├── meta.json          # 元信息（已分析模式、时间戳、版本）
    ├── 文件模式.json      # 文件依赖图 graphData
    └── 功能模式.json      # 功能模块图 graphData
```

meta.json 结构：
```json
{
    "plugin_name": "MyPlugin",
    "file_mode_analyzed": true,
    "function_mode_analyzed": false,
    "file_mode_time": "2026-06-25T10:30:00",
    "function_mode_time": null,
    "version": 1
}
```

### 5.4 资源生命周期管理

可视化引擎使用懒加载策略，避免不必要的资源消耗：

```
用户打开可视化面板
    │
    ▼
[检查库是否已加载] → 否 → CDN 异步加载 3d-force-graph
    │                    │
    │                    ▼
    │                 加载完成
    │
    ▼
[创建图实例] → 渲染 graphData
    │
    ▼
用户切换到其他 Tab
    │
    ▼
[销毁图实例] → graph._destructor()
    │  释放 Three.js WebGL 上下文
    │  移除 DOM 元素
    ▼
资源释放完成
```

> **注意**：3d-force-graph 库本身（约 500KB）加载后缓存在内存中，不会重复下载。但每个图实例的 WebGL 上下文必须显式销毁，否则会导致 GPU 内存泄漏。

## 六、最佳实践和反模式

### 6.1 最佳实践

1. **先文件模式后功能模式**：文件模式快速且准确，适合初步了解插件结构；功能模式需要 AI 调用，适合深度理解

2. **合理控制图规模**：节点超过 100 个时，考虑启用目录聚类折叠，避免视觉混乱

3. **错误优先**：如果存在红色连线（导入错误），优先处理这些依赖问题

4. **双模式交叉验证**：文件模式显示的依赖关系应与功能模式的模块依赖一致，不一致可能意味着代码组织问题

5. **资源清理**：面板切换时必须调用 `销毁图()` 释放 WebGL 资源

### 6.2 反模式

1. **过度依赖 AI 分析**：功能模式的结果是 AI 推断的，可能不准确。应以文件模式（AST 精确解析）为基准

2. **忽视错误连线**：红色连线表示导入失败，可能是循环依赖或路径错误，不应忽略

3. **在循环中重复创建图实例**：
```javascript
// 反模式：每次数据更新都创建新实例
function updateView(data) {
    const graph = 创建可视化图(container, data);  // 每次都新建！
}

// 正确做法：复用实例，更新数据
let graph = null;
function updateView(data) {
    if (!graph) {
        graph = 创建可视化图(container, data);
    } else {
        更新图数据(graph, data);
    }
}
```

4. **不销毁旧实例就创建新实例**：会导致 WebGL 上下文堆积，最终浏览器崩溃

5. **在可视化面板外引用图实例**：图实例的生命周期应与面板绑定，面板关闭即销毁
