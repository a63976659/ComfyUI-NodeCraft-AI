# 插件模板效果实现详解

按「效果」组织的技术词条，提炼自 NodeCraft AI 生产验证的插件实现模式（其中模型缓存、folder_paths 等模式在模板市场内置模板 `后端/模板市场.py` 的 `BUILTIN_TEMPLATES` 中也有落地）。每个词条回答三个问题：**这是什么效果、技术上怎么实现、优点在哪**。开发插件时按需组合使用。

---

## 效果 1：节点里发异步网络请求不报错不卡死

**效果**：节点能调用外部 HTTP API，无论 ComfyUI 以同步还是异步方式执行节点都不会崩溃。

**技术实现**：ComfyUI 节点执行方法是同步的，直接 `asyncio.run()` 遇到"已在事件循环中"会抛 `RuntimeError`。先探测事件循环状态再分流：无循环直接 `asyncio.run`；已在循环中则把 `asyncio.run` 提交到线程池，在新线程里建独立循环执行，主线程用 `future.result(timeout=...)` 限时等待。

```python
loop = asyncio.get_event_loop()
if loop.is_running():
    with concurrent.futures.ThreadPoolExecutor() as executor:
        future = executor.submit(asyncio.run, self._async_call(...))
        result = future.result(timeout=超时时间 + 10)  # 留余量防死等
else:
    result = asyncio.run(self._async_call(...))
```

**优点**：一份代码兼容两种执行环境，不会因部署方式不同而偶发崩溃；超时兜底防止线程永久挂起拖死整个队列。

## 效果 2：网络请求失败自动重试，不会永久挂起

**效果**：偶发网络抖动时节点自动重试并最终拿到结果；彻底失败时给出明确错误而非无限等待。

**技术实现**：`aiohttp.ClientTimeout(total=秒数)` 控制整体超时；for 循环重试，捕获 `asyncio.TimeoutError` / `aiohttp.ClientError` 分类记录，每次失败后 `await asyncio.sleep(RETRY_DELAY * attempt)`——等待间隔随次数线性增长（指数退避思想）；重试耗尽后返回结构化错误 JSON。

```python
client_timeout = aiohttp.ClientTimeout(total=超时时间)
for attempt in range(1, MAX_RETRIES + 1):
    try:
        async with aiohttp.ClientSession(timeout=client_timeout) as session:
            ...  # 发请求，成功即 return
    except asyncio.TimeoutError:
        last_error = f"请求超时（{超时时间}秒）"
    except aiohttp.ClientError as e:
        last_error = f"网络错误: {str(e)}"
    if attempt < MAX_RETRIES:
        await asyncio.sleep(RETRY_DELAY * attempt)
return (json.dumps({"error": last_error, "retries": MAX_RETRIES}, ensure_ascii=False), "{}", -1)
```

**优点**：递增间隔避免失败时疯狂打爆对方服务器；区分超时与网络错误便于排查；最终必然有返回值，工作流不会吊死。

## 效果 3：密钥不出现在节点界面上

**效果**：API Key 等敏感参数不在节点 UI 显示，用户看不到也误改不了，但仍能注入使用。

**技术实现**：INPUT_TYPES 的 `hidden` 段声明隐藏输入，ComfyUI 不为其渲染控件；执行方法签名正常接收该参数，值由工作流 API 注入或从其他节点连线传入。

```python
"hidden": {
    "api_key": "API_KEY",     # 不渲染 UI，外部注入
    "unique_id": "UNIQUE_ID", # ComfyUI 自动注入的节点唯一 ID
}
```

**优点**：敏感信息与 UI 解耦，截图分享工作流不泄露密钥；`UNIQUE_ID` 是官方机制，免费获得节点身份用于日志与状态追踪。

## 效果 4：节点出错不中断整条工作流

**效果**：单个节点失败时，下游拿到的是可读的错误信息而非整个队列崩溃。

**技术实现**：执行方法内全量 try/except，所有错误路径都转成**结构化返回值**（错误 JSON 或可读文本），绝不向外抛异常；状态码输出位用 `-1` 等哨兵值标记失败。

```python
except Exception as e:
    logger.error("API 调用失败: %s", e)
    return (json.dumps({"error": str(e)}, ensure_ascii=False), "{}", -1)
```

**优点**：错误变成数据可被下游节点条件分支处理（如"失败则走备用方案"）；`ensure_ascii=False` 保证中文错误信息可读。

## 效果 5：下拉列表自动显示本机可用的模型文件

**效果**：节点上的模型选择框自动列出用户实际拥有的 checkpoint/VAE/LoRA 文件，不用手输路径。

**技术实现**：调 ComfyUI 官方 `folder_paths.get_filename_list(类型)` 枚举模型目录，返回值直接作为 COMBO 控件选项；列表为空时塞入 `"(无可用模型)"` 占位项，执行时判占位跳过。

```python
checkpoints = folder_paths.get_filename_list("checkpoints") or ["(无可用模型)"]
# INPUT_TYPES:  "Checkpoint模型": (checkpoints,)
# 执行时:      if 模型名 != "(无可用模型)": ...
```

**优点**：跟着 ComfyUI 的模型目录配置走，用户把模型放哪都能找到；占位项保证空目录时控件依然合法可渲染。

## 效果 6：模型路径解析安全，不会读错文件或崩溃

**效果**：用户选的模型名一定能解析成真实存在的文件路径，选错/文件被删时给出清晰报错。

**技术实现**：不自己拼路径，用 `folder_paths.get_full_path(类型, 文件名)` 由官方解析；拿到路径后再 `os.path.isfile` 二次校验，不通过就抛带上下文的 `FileNotFoundError`。

```python
full_path = folder_paths.get_full_path(model_type, model_name)
if not (full_path and os.path.isfile(full_path)):
    raise FileNotFoundError(f"模型文件不存在: {model_type}/{model_name}")
```

**优点**：规避路径拼接的跨平台与目录穿越问题；错误信息带类型和文件名，用户一眼知道去哪补文件。

## 效果 7：同一模型不重复加载，省显存省时间

**效果**：工作流里多个节点用同一模型时只从磁盘加载一次，后续秒级命中。

**技术实现**：模块级字典做缓存，键用「类型:完整路径」保证唯一；执行时先查缓存，未命中才真正加载并存入。

```python
_MODEL_CACHE: Dict[str, Any] = {}

cache_key = f"ckpt:{ckpt_path}"
if cache_key in _MODEL_CACHE:
    model_data = _MODEL_CACHE[cache_key]
else:
    model_data = load_checkpoint_guess_config(ckpt_path, ...)
    _MODEL_CACHE[cache_key] = model_data
```

**优点**：模块级字典跨节点实例共享，生命周期与进程一致；键含路径，换模型自动换缓存，不会串数据。

## 效果 8：自动选择 GPU 或 CPU 运行

**效果**：有显卡用显卡，没有自动落到 CPU，用户零配置。

**技术实现**：一行探测：

```python
def _get_device() -> torch.device:
    return torch.device("cuda") if torch.cuda.is_available() else torch.device("cpu")
```

**优点**：同一份插件代码在高低配机器上都能跑，无需用户改参数。

## 效果 9：只对图像遮罩区域应用处理效果

**效果**：传入遮罩时效果只作用于遮罩区域，其余像素保持原样。

**技术实现**：先把遮罩维度对齐到图像 `[B, H, W, C]`——无批次维 `unsqueeze(0)`，再 `unsqueeze(-1)` 扩出通道维；然后用线性混合公式 `原图*(1-遮罩) + 处理结果*遮罩`，遮罩值 0~1 天然充当混合权重。

```python
if 遮罩.dim() == 2:
    遮罩 = 遮罩.unsqueeze(0)      # [H, W] -> [1, H, W]
if 遮罩.dim() == 3:
    遮罩 = 遮罩.unsqueeze(-1)     # [B, H, W] -> [B, H, W, 1]
processed = 图像 * (1 - 遮罩) + processed * 遮罩
```

**优点**：纯张量运算无循环，GPU 上高效；两种遮罩形状（带/不带批次维）都兼容；遮罩灰度值还自带羽化过渡，边缘不生硬。

## 效果 10：图像处理结果不产生过曝/色块瑕疵

**效果**：任何强度参数下输出图像颜色都合法，不会出现 >1 的白块或 <0 的黑块。

**技术实现**：所有像素运算结束后统一 `clamp(0, 1)` 收拢值域（ComfyUI 图像约定为 float32 范围 0~1）。

```python
processed = processed.clamp(0, 1)
```

**优点**：一行代码兜底所有上游运算的越界风险，防止下游保存/预览节点拿到非法数据出图损坏。

## 效果 11：参数变化才重新执行节点（智能缓存）

**效果**：没改关键参数时节点命中缓存瞬间完成；改了对应参数自动重算，结果永远正确。

**技术实现**：`IS_CHANGED` 方法按场景返回不同值，ComfyUI 用返回值判断是否需要重执行——三种策略：

| 场景 | 返回值 | 原理 |
|---|---|---|
| 结果随时变化（网络调用、随机数） | `float("nan")` | NaN 与任何值都不相等 → 每次必重算 |
| 结果由多个参数决定 | 参数拼签名串 `f"{a}|{b}|{c}"` | 任一参数变化签名即变 |
| 纯计算节点 | 直接返回关键参数值 | 值变了才重算 |

**优点**：把缓存策略显式化，避免"改了参数没生效"或"没改也反复重算"两个方向的 bug。

## 效果 12：一个节点提供多种功能，下拉切换

**效果**：用户用一个节点完成多种文本操作（替换/编码/解码/拼接），不用在画布上堆四个节点。

**技术实现**：COMBO 控件定义「处理模式」选项，执行方法内 if/elif 分发到各自的静态方法；不同模式专属的参数放 optional，不相关时留空即可。

```python
"处理模式": (["模板替换", "编码", "解码", "文本拼接"], {"default": "模板替换"}),
# 执行时
if 处理模式 == "模板替换":
    result = self._apply_template(文本, 模板变量)
elif 处理模式 == "编码":
    result = self._encode_text(文本, 编码类型)
```

**优点**：画布更整洁、节点间连线更少；新增功能只需加一个分支和一个 COMBO 选项，扩展成本低。

## 效果 13：用户输入非法内容时优雅降级不崩溃

**效果**：解码坏数据、模板变量缺失时节点不报错，返回可读提示或原文本。

**技术实现**：所有解析点包 try/except 并给降级出口——解码失败返回 `"[解码失败] 输入不是有效的 Base64 文本"`；`str.format` 模板替换捕获 `(KeyError, IndexError, ValueError)` 后返回原文本。

```python
try:
    return base64.b64decode(text).decode("utf-8")
except Exception:
    return "[解码失败] 输入不是有效的 Base64 文本"
```

**优点**：错误信息直接出现在下游文本里，用户不用翻日志就知道哪一步坏了；工作流不因一处输入问题整体失败。

## 效果 14：节点界面上出现自定义按钮/控件

**效果**：节点上渲染出自定义的按钮，用户点击即触发操作。

**技术实现**：前端用 `getCustomWidgets` 注册 widget 工厂，widget 对象三要素——`draw` 用 canvas 画外观（坐标相对节点左上角）、`mouse` 处理点击并 `return true` 表示已消费事件、`value` 提供可序列化的值。

```javascript
async getCustomWidgets() {
    return { "custom_ui:button_widget": createButtonWidget };
}
// widget.mouse 中：
if (event.type === "pointerdown") {
    api.fetchApi("/插件名/action", { method: "POST", body: JSON.stringify({ action: "click", node_id: node.id }) });
    return true;
}
```

**优点**：完全融入 ComfyUI 原生 canvas 渲染体系，跟随节点缩放/选中/序列化，不需要额外 DOM 层。

## 效果 15：前端按钮一点，后端立即执行

**效果**：点击前端控件触发后端 Python 逻辑并拿到结果。

**技术实现**：后端把路由挂到 `PromptServer.instance.routes`（复用 ComfyUI 自带服务器，无需另起端口）；前端用 `api.fetchApi(路径, {method, body})` 请求，后端返回统一 `{success, data/message}` 结构。

```python
routes = PromptServer.instance.routes

@routes.post("/插件名/action")
async def 执行操作(request):
    data = await request.json()
    return web.json_response({"success": True, "message": f"已执行: {data.get('action')}"})
```

**优点**：零额外基础设施，路由与 ComfyUI 同端口同生命周期；`success` 字段让前端错误处理只有一种写法。

## 效果 16：后端主动推送消息到前端界面

**效果**：后端任务完成/进度变化时，前端界面实时更新，无需轮询。

**技术实现**：复用 ComfyUI 内置 WebSocket——后端 `PromptServer.instance.send_event("事件名", 数据)` 推送，前端 `api.addEventListener("事件名", cb)` 监听，数据在 `event.detail`。

```javascript
api.addEventListener("custom_ui_event", (event) => {
    console.log("收到后端事件:", event.detail);
});
```

**优点**：搭现成的 WebSocket 连接，不新增连接管理成本；事件驱动比轮询省资源、延迟低。

## 效果 17：侧边栏挂自定义入口按钮，打开浮动面板

**效果**：ComfyUI 侧边栏出现插件专属按钮，点击弹出居中浮动面板展示后端数据。

**技术实现**：在扩展的 `setup()` 钩子（应用启动完成后执行）里向 `.comfy-menu` 侧边栏 append 按钮；面板用 `position: fixed + transform: translate(-50%, -50%)` 居中；数据用 `fetch` 拉后端 GET 接口填充。

```javascript
async setup() {
    const sidebar = document.querySelector(".comfy-menu");
    sidebar?.appendChild(btn);  // btn.click -> openCustomPanel()
}
```

**优点**：`setup` 钩子保证 DOM 已就绪，无需自己等待时序；纯 DOM 实现不依赖任何框架。

## 效果 18：面板开关切换不叠加重复弹窗

**效果**：反复点击面板按钮时，面板在打开/关闭间切换，永远不会叠出多个。

**技术实现**：打开前先按固定 id 查已有实例，存在就移除并返回（toggle 语义），不存在才创建。

```javascript
const existing = document.getElementById("custom-ui-panel");
if (existing) { existing.remove(); return; }
```

**优点**：一个 id 常量同时解决"防重复"和"关闭"两件事，无需维护额外的开关状态变量。

## 通用约定（所有效果共同遵守）

1. **节点执行方法永不抛异常**：错误一律转结构化返回值
2. **中文标识**：类名 `中文名_Node`、映射键中文、显示名 `"emoji 中文名 (EnglishHint)"`、参数与 COMBO 选项中文、注释中文
3. **日志分级**：模块级 `logger`，成功 info、重试 warning、未知错误 error
4. **DESCRIPTION 必写**：一句话功能说明，UI 直接展示
5. 可运行脚手架用开发面板“从模板创建”生成（`后端/模板市场.py` 的 `BUILTIN_TEMPLATES`）；本文档的高级模式（重试、密钥注入、Python-JS 通信等）在其基础上按需添加
