# 优化验收与回归清单

> **定位**：任何优化任务**收尾前必须走完**的验收与回归流程。
> 优化力度分档见《项目规模分级优化方案》；代码去重专项的测量-复测特化流程见《重复代码率降低方法论》。

## 一、通用五步闭环

任何优化任务（性能、去重、结构调整）都走同一条闭环：

```
1. 定基线   → 用工具记录改动前的客观数据（耗时/显存/重复率/文件行数）
2. 改动     → 单点小步，一次只改一类问题
3. 逐文件验证 → 每改完一个文件立即做语法检查
4. 全量静态检查 → ruff / node --check 全库跑一遍
5. 同口径复测 → 用与第 1 步完全相同的命令和参数复测，输出对照
```

两条不可退让的规则：

- **没有基线不动手**——凭感觉的「优化」无法证明有效，也无法发现负优化。
- **没有复测不结题**——只说「已优化」而给不出前后数据的交付是不完整的。

## 二、逐文件即时验证

每改完**一个**文件立刻验证，禁止批量改完再统一验证——后者出错时定位成本高出数倍。

Python：

```bash
python -c "import ast; ast.parse(open(r'<文件路径>', encoding='utf-8').read()); print('syntax OK')"
```

JavaScript ES 模块（`node --check` 默认按 CommonJS 解析会误报 `import`）：

```powershell
Get-Content <文件.js> -Raw -Encoding UTF8 | node --input-type=module --check
```

**PowerShell 环境注意**：

- `node --check < 文件` 这种 `<` 输入重定向在 PowerShell 中不可用，会报 `The '<' operator is reserved for future use`。
- 管道方式若因编码或环境失败，可靠兜底是复制成 `.mjs` 再检查（`.mjs` 后缀让 node 直接按 ESM 解析）：

```powershell
Copy-Item <文件.js> $env:TEMP\check.mjs; node --check $env:TEMP\check.mjs
```

**禁止假通过**：不要用 `vm.SourceTextModule` 之类的探测式脚本自证语法正确——缺少 `--experimental-vm-modules` 时它会静默回退，脚本照样打印「通过」，但实际上一行都没解析。任何「验证通过」的结论都必须来自会因语法错误而失败的命令。

## 三、全量静态检查

```bash
python -m ruff check <后端目录> <其他Python目录>
```

重点确认：未使用的导入、未定义的名称、重构后遗留的旧引用。

- **不得为了「更严格」擅自扩大规则集**。项目现有的 lint 配置是与代码风格匹配过的；临时扩大规则会产出大量与本次优化无关的报错，把真问题淹没，也会诱导你去改与任务无关的代码。
- 前端：遍历前端目录逐个 `node --check`（ESM 口径），记录检查文件数与失败数，两个数字都要写进报告。

任何一项失败必须先修复再继续，禁止带错进入下一步。

## 四、行为等价性自检

优化（尤其是重构类）**不允许改变外部可观察行为**。改完后逐项对照原代码：

| 对照项 | 要求 |
|---|---|
| 日志文本 | 逐字一致，包括标点与占位符 |
| 错误响应结构 | 字段名、嵌套层级、状态码不变 |
| 返回值结构 | 元组元素顺序、字典键名不变 |
| 提示文案 / i18n key | 不变 |
| 默认参数值 | 不变 |
| 抛出的异常类型 | 不变（前端可能按类型分支处理） |

两处代码 90% 相同但有 10% 差异时，差异必须用**参数或回调显式保留**，**禁止「顺手统一」**——统一日志格式、统一错误结构这类改动看起来更整洁，实际是行为变更，会破坏调用方解析。

## 五、功能回归清单（按插件形态分档）

只测与改动相关的部分，但下表对应形态的项目**不能跳过**：

| 形态 | 必测项 |
|---|---|
| 节点插件 | 至少 3 组不同输入组合各跑一次完整工作流；若涉及 `IS_CHANGED` / `fingerprint_inputs`，缓存命中与缓存失效两条路径都要验 |
| 有前端 | **硬刷新清缓存**后再验证；检查浏览器控制台无新增报错；改动涉及布局时目视确认无叠压/溢出 |
| 有后端路由 | **重启 ComfyUI** 后逐个请求受影响接口，确认不是 404、返回结构与改动前一致 |
| 有持久化数据 | 用改动**之前**产生的旧数据验证兼容性，确认不丢、不错、不需要用户手工迁移 |

两个高频误判：

- **前端改完不清缓存**：浏览器 JS 缓存会造成双向假象——既可能让已生效的修复看起来「没生效」，也可能让失败的修复看起来「已修复」。
- **后端改完不重启**：Python 模块已加载在内存里，改了文件而不重启，跑的仍是旧代码，测出的结论无效。

## 六、性能类优化的复测口径

- 同一台机器、同一批输入、同样的 warmup 次数与运行轮数
- 涉及 GPU 必须 `torch.cuda.synchronize()` 后计时，否则测到的是异步下发耗时
- 复测命令与基线命令**逐字相同**，参数不得调整

具体计时代码、Profiling 工具用法与量化目标见《性能基准与Profiling指南》，本文不重复。

## 七、回退准备（动手之前先做）

优化是多点改动，必须先确认「改坏了怎么退回去」。

先确认目标目录是否被 git 跟踪：

```bash
git ls-files <目录>
```

返回空说明该目录**不在 git 跟踪范围内**，`git checkout -- <路径>` 与 `git stash` 都无法回退（ComfyUI 的 `custom_nodes` 子目录经常属于这种情况——外层仓库的 `.gitignore` 忽略了它）。

- **已跟踪**：改动前确认工作区干净，出问题用 `git checkout --` 或 `git diff` 逐项核对。
- **未跟踪**：改动前整目录备份一份；或在报告里给出「文件清单 + 每处改动的前后内容」，保证人工可逆。**不要假设可以 git 回退**。

## 八、交付报告模板

1. **变更文件清单** + 每个文件的验证结果（语法检查、静态检查是否通过）
2. **基线 vs 复测对照表**（耗时 / 显存 / 重复率 / 行数，视任务类型选取）
3. **是否达成目标**（用户给了阈值就明确答成/未成，未成说明差距与原因）
4. **刻意未做的项 + 理由**：收益递减 / 越档（见《项目规模分级优化方案》红线）/ 风险高 / 需用户决策
5. **需要用户手工完成的事项**：重启 ComfyUI、安装依赖、下载资源、清浏览器缓存

第 4 项最容易被省略，但它恰恰是让用户能判断「优化是否到位」的关键——不写等于让用户以为全都做了。

## 九、常见踩坑

| 坑 | 规避 |
|---|---|
| 前端改完不清缓存，验证结论完全错误 | 硬刷新后再验 |
| 后端改完不重启，跑的还是内存里的旧代码 | 重启 ComfyUI 后再验接口 |
| 批量改完再统一验证，报错难定位 | 每改一个文件立即验证 |
| 擅自扩大 lint 规则集，真问题被淹没 | 沿用项目现有配置 |
| 假设可以 git 回退，实际目录未被跟踪 | 动手前 `git ls-files` 确认，未跟踪先备份 |
| 重构时「顺手」统一了日志/错误格式 | 差异参数化保留，改前逐字 diff |
| 只报「已优化」不给前后数据 | 同口径复测 + 对照表 |
