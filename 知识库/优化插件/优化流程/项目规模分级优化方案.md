# 项目规模分级优化方案

## 概述

不同规模的 ComfyUI 插件需要匹配不同力度的优化策略。**给小项目套用大项目的重型方案，是最常见、代价最高的错误**——它会带来无谓的复杂度、更多的 Bug 面、更长的维护成本，却换不来任何用户可感知的收益。

本文档的目标：先让智能体**准确判断项目规模**，再据此**匹配对应档位的优化方案**，并明确划出"过度优化"的红线。

> **黄金准则**：优化力度应与项目复杂度、用户规模、数据重要性成正比。判不准规模时，**默认按低一档处理**，宁可少做，不可滥做。

---

## 一、如何判断项目规模（必须先执行）

智能体在给出任何优化建议前，**必须先完成规模判断**。判断依据来自"项目上下文分析"注入的结构化信息（文件树、注册节点、模块依赖、前端文件），不要凭主观印象。

### 1.1 三类插件形态与默认规模

| 插件形态 | 典型特征 | 默认规模档位 |
|---------|---------|:---:|
| **基础节点类型插件** | 纯 Python 计算/转换节点，接收输入→处理→输出，无前端或仅少量自定义 Widget | 🟢 小项目 |
| **顶部菜单栏 / 状态信息类型插件** | 有 `registerCommand`（菜单命令）或 `addStatusBarItem`（状态栏），前端逻辑轻量，无独立数据面板 | 🟡 中小型项目 |
| **侧边栏类型插件** | 用 `registerSidebarTab` 把一整套应用嵌入侧边栏容器，包含独立前后端、持久化数据、复杂交互 | 🔴 大项目 |

> 插件形态是**首要信号**，但不是唯一依据。必须结合下面的量化信号交叉验证——有的"节点插件"也可能演化成大项目。

### 1.2 量化信号（交叉验证规模）

从项目上下文中提取以下客观指标，命中越多、越靠右，规模越大：

| 信号维度 | 🟢 小项目 | 🟡 中小型 | 🔴 大项目 |
|---------|---------|---------|---------|
| Python 源文件数 | ≤ 3 | 4 ~ 10 | > 10 |
| 注册节点数（NODE_CLASS_MAPPINGS） | 1 ~ 3 | 4 ~ 10 | 与前端应用解耦，节点非核心 |
| 前端 JS | 无 / 单文件 Widget | 单文件命令或状态项 | 多文件、独立 UI 目录 |
| 前端能力 | 无 或 自定义 Widget | registerCommand / StatusBar | registerSidebarTab + 独立应用 |
| 数据持久化 | 无 | 少量本地配置（settings） | 会话/文件/数据库，需保证不丢失 |
| 后端服务 | 无自定义路由 | 少量只读接口 | 自定义路由 + WebSocket + 鉴权 |
| 外部依赖/模型 | 无或单一 | 少量 | 多模型、多外部 API |

### 1.3 判定规则

- **全部维度落在🟢列** → 判为**小项目**，采用第二章"基础标准优化方案"。
- **大部分维度落在🟡列，且无 registerSidebarTab、无关键数据持久化** → 判为**中小型项目**，采用第三章方案。
- **出现 registerSidebarTab 嵌入独立应用，或存在"数据一旦丢失会造成损失"的持久化，或同时具备自定义后端路由 + WebSocket** → 判为**大项目**，采用第四章"项目级专业优化策略"。
- **信号矛盾/不确定** → 就低不就高，按**低一档**处理，并在回答中说明"当前判断为 X 档，如项目实际更复杂请补充信息"。

## 二、小项目：基础标准优化方案（基础节点类型插件）

**适用**：1~3 个纯计算节点、无前端或仅自定义 Widget 的插件。

**优化目标**：正确、简洁、够快。**不要引入任何架构级设施**。

### 2.1 该做的（标准动作）

- **缓存重复计算**：用 `IS_CHANGED` / `fingerprint_inputs` 控制重执行，输入未变则跳过。
- **张量与显存**：及时 `del` 中间张量，批处理结束后再 `torch.cuda.empty_cache()`，避免循环内频繁调用。
- **批量而非逐张**：多图输入走批处理，减少 CPU/GPU 切换。
- **按需加载模型**：模型延迟加载 + 单例复用，不要在导入时就加载。
- **输入校验**：`VALIDATE_INPUTS` 做基础范围/类型校验，给出清晰报错。
- **长任务进度**：耗时操作用 ComfyUI 进度回调，避免界面假死。

### 2.2 明确不要做（避免过度优化）

- ❌ 不要引入多层缓存、Redis、内存+磁盘分级缓存。
- ❌ 不要为几个节点上事务/锁机制。
- ❌ 不要设计"模块化架构""插件化框架""依赖注入"。
- ❌ 不要写自定义后端路由、WebSocket、鉴权。
- ❌ 不要加骨架屏、SWR、懒加载等前端体验设施（没有复杂前端）。

> 小项目的优化，读完代码 10 分钟内应能说清"哪里慢、怎么改"。如果你的建议需要新增多个文件或框架，多半是过度优化。

## 三、中小型项目：适度增强方案（顶部菜单栏 / 状态信息类型插件）

**适用**：有顶部菜单命令（`registerCommand`）或底部状态栏（`addStatusBarItem`）、前端逻辑轻量、可能有少量本地配置的插件。

**优化目标**：在小项目基础上，增强**交互响应**与**少量状态管理**的健壮性，但仍克制，不上重型架构。

### 3.1 在基础方案之上，增量补充

- **前端响应**：菜单命令/状态项的更新用节流（throttle）或防抖（debounce），避免高频事件卡顿；状态栏轮询改为事件驱动（监听 `status` / 自定义事件）。
- **轻量状态持久化**：用 ComfyUI 设置系统（`app.ui.settings`）或本地 `localStorage` 保存配置，读写做好默认值与异常兜底。
- **只读接口优先**：如需后端数据，优先只读接口 + 前端缓存结果，避免复杂写入路径。
- **错误可见**：命令失败用 Toast 提示，不静默吞异常。
- **懒初始化**：菜单/状态项相关的重逻辑，在用户首次触发时再初始化，不拖慢启动。

### 3.2 边界（不要越档）

- 除非有明确的并发写入与数据丢失风险，否则**不需要事务和锁**。
- 无独立数据面板时，**不需要骨架屏、SWR、虚拟列表**这类大项目体验设施。
- 保持"单文件或少量文件"的前端结构，不要提前拆成多层模块。

## 四、大项目：项目级专业优化策略（侧边栏类型插件）

**适用**：用 `registerSidebarTab` 将一整套应用嵌入侧边栏容器，具备独立前后端、持久化数据、复杂交互、外部服务依赖的插件。

**优化目标**：这类插件本质是"嵌在 ComfyUI 里的完整应用"，需要按**产品级工程标准**从五个维度系统优化——**快、稳、安全、好用、可维护**。

### 4.1 快：多层缓存让首屏响应 < 100ms

- **分级缓存**：内存缓存（热数据）→ 本地磁盘/IndexedDB（温数据）→ 后端（冷数据），命中就近返回。
- **首屏预算**：首屏关键数据 < 100ms 返回；非关键数据延迟加载。用"先渲染缓存、后台刷新"的策略避免白屏。
- **请求合并与去重**：并发相同请求做去重（in-flight 复用）；小请求批量化，减少往返。
- **按需与虚拟化**：长列表用虚拟滚动；重组件懒加载（动态 import）；图片用缩略图 + 渐进加载。
- **索引与增量**：后端检索建索引（如 BM25/向量），文件同步用哈希比对做增量，不做全量重算。

### 4.2 稳：事务和锁确保数据永不丢失

- **写操作原子化**：涉及多步写入用事务；关键文件写入用"临时文件 + 原子 rename"，避免半写状态。
- **并发控制**：对共享资源（会话文件、计数器、余额）加锁或用乐观锁（版本号 CAS），防止并发覆盖。
- **幂等与重试**：网络/外部调用做幂等设计 + 有限重试 + 退避，避免重复扣费或重复写入。
- **崩溃可恢复**：长任务分步落盘，中断后可续；关键状态有校验和/版本号。
- **一致性优先于速度**：涉及金额、余额、用户数据时，宁可慢一点也要保证不丢、不错。

### 4.3 安全：多层防线形成纵深防御

- **输入校验**：前端校验（体验）+ 后端强校验（安全），永远不信任前端传入。
- **鉴权与最小权限**：接口鉴权（token/JWT），路径操作限制在允许目录内，防目录穿越。
- **注入防护**：文件路径、命令、模板渲染均做转义/白名单；前端渲染用 DOMPurify 防 XSS。
- **敏感信息**：密钥不落前端、不进日志；日志做脱敏；配置与密钥分离存储。
- **限流与审计**：对外/高成本接口做限流；关键操作写审计日志，可追溯。

### 4.4 好用：细节处处为用户体验考虑

- **骨架屏**：加载态用骨架屏替代空白/转圈，降低等待焦虑。
- **SWR（stale-while-revalidate）**：先展示缓存数据，后台静默刷新，用户几乎无感知延迟。
- **懒加载**：路由/面板/重组件按需加载，首屏只加载必要资源。
- **乐观更新**：用户操作先本地即时反馈，后台异步落库，失败再回滚并提示。
- **反馈闭环**：加载/成功/失败/空态都有明确 UI；长任务有进度；错误可读、可重试。

### 4.5 可维护：模块化设计 + 完善文档

- **模块化分层**：前端按"视图 / 状态 / 服务 / 工具"分层，后端按"路由 / 业务 / 数据 / 公共"分层，单文件职责单一。
- **清晰边界**：模块间通过明确接口通信，减少循环依赖；公共逻辑抽取复用。
- **文档齐全**：架构说明、接口文档、关键决策与"踩坑记录"沉淀成文档，降低后续维护与协作成本。
- **可测试与可观测**：关键路径可测试；接入性能监控与日志，问题可定位。
- **渐进演进**：优化分批落地，每步可回退，不做一次性大重构。

### 4.6 大项目优化的落地顺序

按"投入产出比"排序，避免一上来就做最重的事：

1. 先补**稳/安全**的底线（数据不丢、不被攻破）——这是不可退让的红线。
2. 再做**快**的高频路径（首屏、热点接口）——用户最能感知。
3. 然后打磨**好用**的体验细节（骨架屏、SWR、懒加载）。
4. 最后沉淀**可维护**（模块化重构、文档）——持续进行。

## 五、过度优化红线（反面清单）

出现以下情况，说明优化"越档"了，应当收敛：

- 给 1~3 个节点的**小插件**引入多层缓存、事务、锁、模块化框架。
- 没有持久化数据，却设计"数据永不丢失"的事务方案。
- 没有独立前端应用，却加骨架屏、SWR、虚拟列表、状态管理库。
- 没有对外接口/敏感数据，却做限流、审计、纵深防御。
- 为"未来可能的扩展"提前抽象，增加了当前并不需要的层级。
- 优化建议引入的新文件/依赖数量，远超原项目本身的规模。

> **判断口诀**：先问"这个项目有没有对应的问题"，再问"用户/数据规模是否值得这个成本"。两个都为"是"才做，否则就是过度优化。

## 六、给智能体的执行清单

面对"优化"类请求时，按顺序执行：

1. **读上下文**：查看项目结构、注册节点数、前端文件、是否有 `registerSidebarTab` / `registerCommand` / `addStatusBarItem`、是否有持久化与后端路由。
2. **定档位**：按第一章规则判为 小 / 中小型 / 大 项目；信号矛盾时就低不就高。
3. **选方案**：小 → 第二章；中小型 → 第三章；大 → 第四章五维度。
4. **对照红线**：用第五章反面清单自检，剔除越档建议。
5. **说明理由**：在回答开头明确"判定规模 + 依据 + 采用的优化档位"，让用户可核对、可纠偏。
