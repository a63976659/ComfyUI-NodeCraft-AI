# 复杂度与大文件拆分

> **定位**：本文管「**该不该拆、按哪个维度拆、怎么保证拆完行为不变**」。
> 重复代码的识别与合并见《重复代码率降低方法论》；拆完后的收尾流程见《优化验收与回归清单》。

## 一、先破除误区：行数不等于缺陷

**「文件太长」不是缺陷，「职责混杂」才是。** 一个 1900 行但只做一件事的模块，可维护性可能远高于
5 个互相调用、边界模糊的 300 行文件。拆分会引入新的导入关系、循环导入风险和调用跳转成本，
**拆错比不拆更糟**。

| 真正该拆的信号 | 不必拆的情况 |
|---|---|
| 改一个功能要在同文件里跨越多个不相关区域反复跳转 | 文件长，但从头到尾都在做同一类事（如一组同族 API 处理函数） |
| 一个模块同时承担路由、业务逻辑、磁盘 IO、外部调用 | 内容是平铺的常量表、映射表、词条库（如 i18n 词条） |
| 顶层定义里能明显分出两组「互不调用」的函数簇 | 只是单个函数过长——那是函数级问题，见第六章，不用动文件 |
| 多人/多任务频繁在同一文件的不同区域产生修改冲突 | 拆开后必须靠 re-export 才能维持调用方不变，且没有其他收益 |

> **红线**：用户只说「优化性能」「降低重复率」时，**不要顺手拆文件**。拆分改变模块结构，
> 属于独立的重构任务，需用户明确要求。这与《项目规模分级优化方案》的过度优化红线一致。

## 二、量化信号：先测量再判断

### 文件级

```bash
# 行数排序（PowerShell，排除第三方 lib）
Get-ChildItem -Recurse -Include *.py,*.js -Path 后端,智能体,前端 |
  Where-Object { $_.FullName -notmatch "\\lib\\" } |
  ForEach-Object { [PSCustomObject]@{ n=(Get-Content $_.FullName).Count; f=$_.Name } } |
  Sort-Object n -Descending | Select-Object -First 15

# 顶层定义数量（职责密度的粗略代理指标）
Select-String -Path 后端\*.py -Pattern "^(def|class) " | Measure-Object
```

### 函数级

```bash
# 圈复杂度：ruff 的 mccabe 规则，不改配置文件的临时用法
python -m ruff check . --select C901 --config "lint.mccabe.max-complexity = 10"
```

| 指标 | 关注阈值 | 处置 |
|---|---|---|
| 圈复杂度（C901） | > 10 | 优先按第六章降复杂度，不必动文件结构 |
| 函数行数 | > 80 行 | 检查是否混了「解析参数 + 业务 + 响应构造」三件事 |
| 嵌套深度 | > 3 层 | 用卫语句提前 return 拉平 |
| 顶层定义数 | 单文件 > 40 个 | 检查能否分出互不调用的函数簇 |
| 位置参数个数 | > 5 个 | 改为关键字参数或参数对象 |

> **阈值是排查起点，不是判决**。超阈值只意味着「值得看一眼」，看完确认职责单一就不动。

## 三、拆分维度（按优先级选一个，不要混用）

1. **按职责／业务功能拆（首选）**——每个新文件用准确表达功能的中文名，如 `认证路由.py`、
   `JSON修复工具.py`。判据：新文件的名字能用一句话说清且不含「和」「等」。
2. **按调用层次拆**——路由层（解析请求 / 构造响应）、业务层、IO 层。适合单文件里
   HTTP 处理与核心算法缠在一起的情况。
3. **按变更频率拆**——把高频改动的配置、映射表、提示词分离出去，让稳定的核心逻辑不被反复触碰。

**反模式**（出现即视为拆错）：

- 按行数机械切成 `xxx_part1.py` / `xxx_part2.py`
- 造 `utils.py` / `common.py` / `helpers.py` 之类无职责的垃圾桶模块
- 拆完后两个文件互相 import 对方的函数（说明边界划错了，应回退重划）

## 四、Python 拆分标准流程

1. **列清单**：先把待拆文件的顶层定义全部列出，标注每个属于哪个职责簇，以及被哪些外部模块引用。
2. **定边界**：按第三章选一个维度，确认簇之间**单向依赖**（新模块可以依赖公共模块，但不能互相依赖）。
3. **搬代码**：整段移动，**不趁机改逻辑**（改名、改日志、改默认值一律禁止）。
4. **留导航**：原文件 docstring 说明本模块剩余职责，并列出拆出去的模块及其内容。
5. **保兼容**：外部调用方可能仍从原模块导入符号，用 re-export 兜住。
6. **验证**：按《优化验收与回归清单》走完整流程，不要自行简化步骤。

第 4、5 步的标准写法（本项目 `后端/文件路由.py` 的实际做法，泛化如下）：

```python
"""文件路由模块

包含纯文件 CRUD 操作：
- POST /ai-coder/read-file      读取文件
- POST /ai-coder/write-file     写入文件

其他路由已拆分至：
- 代码审查路由.py    (code-review, benchmark)
- 插件浏览路由.py    (create-folder, browse, plugins)
"""

# re-export: 保持向后兼容（其他模块可能通过 文件路由 导入这些符号）
from .代码审查路由 import handle_code_review  # noqa: F401
from .插件浏览路由 import handle_browse_folder  # noqa: F401
```

> `# noqa: F401` 必须加，否则 ruff 会把这些「未使用的导入」判为错误。
> 注册函数（如 `register_xxx路由`）也要同步拆分并在入口处逐个调用，漏掉一个就是**静默 404**。

### 循环导入的规避

- 公共依赖（限流器、错误响应、路径校验）下沉到一个**不 import 任何业务模块**的公共模块。
- 确实需要反向引用时，把 import 放进函数体内（延迟导入），并注释说明原因。
- 仅类型注解需要的引用用 `if TYPE_CHECKING:` 包住。

## 五、前端 JS 拆分

- **按功能拆 ES module**：每个文件一个明确职责，用 `export` 暴露，调用方显式 `import`。
  拆完后检查所有相对路径——路径写错在浏览器里表现为整个面板空白，控制台才有 404。
- **样式同步拆**：一个巨大 CSS 拆成按主题命名的多个文件（如 `变量与动画.css`、`消息与聊天.css`），
  用 `@import` 或在入口统一挂载。注意 CSS 后写覆盖先写，**拆分后的加载顺序必须与原顺序一致**。
- **目录化**：同一功能族的多个文件收进子目录（如 `消息渲染/`），子目录内相对路径要一起改。
- 拆分不改变 `WEB_DIRECTORY` 的对外路径，但改文件名会让浏览器旧缓存失效——回归前**必须硬刷新**。

## 六、函数级降复杂度（不动文件结构的轻量手段）

| 手法 | 适用信号 | 要点 |
|---|---|---|
| 卫语句提前 return | 嵌套 > 3 层，主逻辑被包在最内层 | 先处理异常与边界并 return，主逻辑回到最外层 |
| 抽取小函数 | 函数内有可命名的连续片段 | 抽出后原处只剩一行调用，函数名即注释 |
| 查表替代长分支 | 一串 if-elif 只为按键取值 | 换成 dict 映射；仅当分支体是纯取值时才适用 |
| 参数对象化 | 参数 > 5 个且总是一起传 | 打包成 dataclass 或 dict，调用方同步改 |
| 提取重复片段 | 多处结构相同仅参数不同 | 见《重复代码率降低方法论》，本文不重复 |

> 优先做函数级优化：它不改变模块边界，风险远低于拆文件，很多「文件太乱」的感受
> 其实来自几个超长函数。

## 七、拆分不改行为的硬约束

除《优化验收与回归清单》的通用项外，拆分特有的四个高危点：

| 风险 | 表现 | 防法 |
|---|---|---|
| 模块级副作用被搬走 | 原文件导入时执行的初始化（注册、建目录、读配置）跟着代码走，执行时机变了 | 副作用留在入口模块，或确认新模块一定被导入 |
| 全局单例被复制 | 两个模块各自 `x = Xxx()`，变成两个实例，状态不共享 | 单例定义只留一处，其余全部 import 引用 |
| 相对导入写错层级 | `ImportError: attempted relative import` 或导入到同名的别的模块 | 同包内统一用 `from .模块 import`，跨包用完整路径 |
| 遗漏注册调用 | 路由/节点少注册一组，前端报 404 但后端无报错 | 拆分前后对比注册项数量，逐个核对 |

## 八、检查清单

- [ ] 拆分是用户明确要求的任务，不是在别的优化里顺手做的
- [ ] 已用行数 + 顶层定义数 + 圈复杂度取得基线，而非凭感觉
- [ ] 确认属于「职责混杂」而非「单纯长」
- [ ] 只用了一个拆分维度，新文件名都能用一句话说清职责
- [ ] 簇之间单向依赖，无互相 import
- [ ] 搬代码期间零逻辑改动（含日志文本、默认值、异常类型）
- [ ] 原文件 docstring 留了导航，外部符号用 re-export 兜住并加 `# noqa: F401`
- [ ] 注册函数拆分后逐个调用，数量与拆分前一致
- [ ] 模块级副作用与全局单例已确认未被复制或移位
- [ ] 走完《优化验收与回归清单》的全部步骤

## 九、常见踩坑

| 坑 | 后果 | 规避 |
|---|---|---|
| 按行数机械对半切 | 两个文件互相 import，调用链更难读 | 只按职责切；切不出单向依赖就不切 |
| 拆完忘记 re-export | 其他模块 `ImportError`，或路由静默 404 | 拆前先 grep 谁在导入这个文件的符号 |
| re-export 未加 `# noqa: F401` | ruff 报未使用导入，全量检查不通过 | 每条 re-export 都加 |
| 搬代码时"顺手"统一日志文案 | 行为不等价，用户看到的提示变了 | 搬运与优化分两次做，中间各自验证 |
| CSS 拆分后加载顺序变了 | 样式被错误覆盖，视觉错乱 | 保持与原文件内声明顺序一致 |
| 前端拆分后未硬刷新就回归 | 浏览器用旧缓存，误判「拆分没生效」或「拆坏了」 | Ctrl+F5 或禁用缓存后再测 |
| 遗漏 `__all__` 同步 | `from 模块 import *` 拿不到搬走的符号 | 拆分后同步更新原模块与新模块的 `__all__` |
