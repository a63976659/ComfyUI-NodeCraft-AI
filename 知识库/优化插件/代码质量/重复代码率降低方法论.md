# 重复代码率降低方法论（去重重构标准流程）

> 适用场景：用户要求"降低重复代码率 / 消除重复代码 / 代码去重重构"，并给出目标阈值（如 5% 以下）。
> 本流程为经过实战验证的标准执行顺序，智能体应严格按 5 个阶段依次执行，禁止跳过测量直接改代码。

## 核心原则（先读，全程遵守）

1. **先测量后动手**：没有基线数据不做任何重构，重构效果必须用同一工具、同一参数复测对比。
2. **只重构最大克隆簇**：按 token 数从大到小排序，优先消除收益最高的重复段；剩余小段相似（语义合理的雷同）不强行合并——收益递减且引入回归风险。
3. **严格保持原行为**：日志文本、错误消息格式、提示文案、返回结构等两处调用点间的细微差异，必须用**参数或回调**保留，禁止"顺手统一"。
4. **禁止扩大范围**：不添加任何新功能、UI 或逻辑变更，变更严格限定于去重重构本身。
5. **每改完一个文件立即做语法验证**，全部改完后统一复测重复率。

---

## 阶段 1：基线测量

用 jscpd 扫描目标代码目录（排除第三方库目录），记录基线数据：

```bash
npx --yes jscpd@latest <目录1> <目录2> ... --ignore "**/lib/**" --min-tokens 50 --reporters consoleFull --format "python,javascript" --output .jscpd-report
```

参数说明：
- `--min-tokens 50`：过滤掉琐碎小段，只关注有重构价值的克隆
- `--ignore "**/lib/**"`：排除第三方库/依赖目录（按项目实际调整）
- `--format`：按项目语言调整（python / javascript / typescript 等）

**必须记录**：总重复率（行 % 和 token %）、克隆总数。这是后续对比的唯一基准。

> 若基线已低于目标阈值，仍应继续重构主要克隆簇（用户要求的是"降低"），但可提前告知用户已达标。

## 阶段 2：热点分析（按 token 排序定位最大克隆簇）

用 JSON reporter 重跑并排序，得到按价值排序的重构清单：

```bash
npx --yes jscpd@latest <目录...> --ignore "**/lib/**" --min-tokens 50 --reporters json --format "python,javascript" --output .jscpd-report
```

然后用 node 脚本读取 `.jscpd-report/jscpd-report.json`，按 `tokens` 字段降序排序，输出每处克隆的两个位置（文件+行范围）。

> 踩坑：`--reporters consoleFull` 不会生成 JSON 文件，必须显式用 `--reporters json`。

分析时将克隆分为三类，决定处理策略：
- **文件内克隆**（同文件两段重复）→ 提取为该文件的私有辅助函数，风险最低，优先做
- **跨文件克隆**（两个文件共享脚手架）→ 提取到公共模块（工具函数文件），注意避免循环依赖
- **语义合理雷同**（如相似但独立演化的配置块、小于 ~100 tokens 的片段）→ 不处理，说明理由

## 阶段 3：重构（核心方法）

### 3.1 提取模式选择

| 重复形态 | 提取方式 |
|---|---|
| 同一函数流程中的重复段（如请求解析、校验链） | 提取为模块级辅助函数，返回 `(结果, None)` 或 `(None, 错误响应)` 元组 |
| 类内两个方法（如流式/非流式两条路径）的重复段 | 提取为类私有方法 |
| 两个前端模块共享的 DOM 脚手架 | 提取到公共工具模块，接受 `onXxx` 回调注入差异逻辑 |
| 循环内的分类/分发逻辑 | 提取为纯函数，返回 `(结果, 标志位)`，循环体只留组装代码 |

### 3.2 保留行为差异的三种手段（关键）

两个调用点 90% 相同、10% 不同时，**差异必须显式参数化**，逐字对比后选择：

1. **布尔标志参数**：如 `流式=False`——内部用 if 分支保留两版日志格式、提示文本的差异
2. **回调参数**：如 `onCancel` / `onConfirm` / `错误400=某错误构造函数`——调用点注入各自的差异逻辑
3. **默认值参数**：如 `任务名="跨会话记忆提取"`——另一调用点传 `任务名="跨会话记忆提取(流式)"`

反例（禁止）：发现两处错误响应格式不同（`{"error": msg}` vs `{"message": msg, "data": None}`），为省事统一成一种——这是行为变更，会破坏前端解析。正确做法是保留两个构造函数，用回调参数注入。

### 3.3 执行细节

- 新函数插入位置：紧邻原调用点所在函数之前，或放在文件既有的辅助函数区域，遵循原文件组织习惯
- 提取时**逐行复制原代码**，不重写、不"优化"表达式，注释原样保留
- 每个文件改完立即验证（见阶段 4 的单文件验证命令），再改下一个文件
- 前端 ES 模块提取公共函数时检查 import 关系，公共函数放在被双方都已依赖的底层模块（如工具函数文件），避免新增循环依赖

## 阶段 4：语法与静态检查（每文件即时 + 最终全量）

Python（每改完一个文件立即执行）：

```bash
python -c "import ast; ast.parse(open(r'<文件路径>', encoding='utf-8').read()); print('syntax OK')"
```

JavaScript ES 模块（`node --check` 默认按 CommonJS 解析会误报 import，需用 stdin + module 模式）：

```powershell
Get-Content <文件.js> -Raw -Encoding UTF8 | node --input-type=module --check
```

最终全量静态检查（重点确认无未使用导入、无未定义名称）：

```bash
python -m ruff check <后端目录> <其他Python目录>
```

任何一项失败必须先修复再继续，禁止带错进入下一阶段。

## 阶段 5：复测与结论

用**与阶段 1 完全相同的命令和参数**复测：

```bash
npx --yes jscpd@latest <目录...> --ignore "**/lib/**" --min-tokens 50 --reporters consoleFull --format "python,javascript" --output .jscpd-report
```

输出结论必须包含：

1. 基线 vs 复测对照表（行重复率、token 重复率、克隆数）
2. 是否达到目标阈值
3. 变更文件清单 + 每个文件的验证结果
4. 剩余克隆的说明（为何不继续消除：语义合理雷同 / 收益递减 / 合并风险）

## 完整执行顺序速查

```
1. jscpd 基线扫描 → 记录 行%/token%/克隆数
2. jscpd --reporters json 重跑 → 按 tokens 降序排出克隆清单
3. 按簇从大到小重构：
   a. 读两处克隆代码，逐字对比找出差异点
   b. 选提取模式（模块函数/类方法/回调注入）
   c. 差异用 布尔标志/回调/默认值参数 显式保留
   d. 改完立即 ast.parse / node --check 验证
4. 全量 ruff check
5. 同参数 jscpd 复测 → 输出基线对比结论
```

## 常见踩坑

| 坑 | 规避 |
|---|---|
| jscpd consoleFull 不产出 JSON | 排序分析必须用 `--reporters json` |
| node --check 对 import 语法报错 | 用 `--input-type=module` + stdin 方式 |
| 提取时"顺手"统一了两处的日志/错误格式 | 差异必须参数化保留，重构前逐字 diff 两段代码 |
| 前端公共函数提取引入循环依赖 | 放到双方共同依赖的底层工具模块 |
| 追求消除全部克隆 | 只做 token 数最大的簇，剩余小段说明理由即可 |
| SearchReplace 因空格/横线数不匹配失败 | 以函数签名等稳定代码行为锚点，不含装饰性注释行 |
