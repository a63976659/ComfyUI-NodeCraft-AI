# 启动与导入优化

> **定位**：本文管**加载期与主线程**——插件被 ComfyUI 导入时的开销、依赖声明、以及不阻塞事件循环。
> 执行期的 GPU 层面优化见《ComfyUI性能调优实战》；计时与 Profiling 工具用法见《性能基准与Profiling指南》。

## 一、为什么启动期要单独优化

ComfyUI 在启动时会**逐个串行导入** `custom_nodes` 下的每个插件包。这带来两个与执行期完全不同的后果：

- **耗时会直接叠加到 ComfyUI 的启动时间上**。某个插件导入耗时 3 秒，用户感知到的是「ComfyUI 启动变慢了 3 秒」，而不是「某插件慢」——问题不容易被归因到插件本身，但体验损失是真实的。
- **导入期抛异常比慢更严重**。模块导入失败会让整个插件包被标记为加载失败，节点在菜单里直接消失、前端目录也不会被挂载。用户看到的是「插件坏了」。

判定阈值（单个插件包的导入耗时）：

| 耗时 | 结论 |
|---|---|
| < 200ms | 合格，无需优化 |
| 200ms ~ 1s | 可接受，但应排查是否有可延迟的重依赖 |
| > 1s | 必须优化 |

## 二、测量导入开销

### 用 -X importtime 定位最重的依赖

标准库自带的导入计时，不需要装任何工具：

```bash
# 在 ComfyUI 根目录执行（保证 sys.path 与实际运行环境一致）
python -X importtime -c "import custom_nodes.你的插件目录名" 2> importtime.log
```

输出三列：`self`（该模块自身耗时，微秒）、`cumulative`（含子导入的累计耗时）、`imported package`。
**按 `cumulative` 从大到小看**，排在最前的就是拖慢启动的元凶（常见是 transformers、diffusers、cv2、pandas、matplotlib）。

### 粗粒度交叉验证

- 临时在 `__init__.py` 首尾夹 `time.perf_counter()` 打印总耗时，确认优化前后的差值。**这是调试代码，交付前必须删除**。
- 对照 ComfyUI 控制台启动日志的时间戳差值，确认测出的耗时与真实启动表现一致。

> 需要看导入期内部的函数级耗时分布时用 cProfile，用法见《性能基准与Profiling指南》，本文不重复。

## 三、`__init__.py` 的四条硬规则

### 规则 1：只注册，不加载

`__init__.py` 的职责只有「声明这个包提供什么」，**不是「把功能准备好」**。

顶层禁止出现：

- 重依赖链的导入（transformers / diffusers / cv2 / pandas / 自建索引库）
- 模型权重加载、`torch.compile`、CUDA 上下文初始化
- 读取大文件、递归扫描磁盘、建立数据库连接
- 任何网络请求（检查更新、拉取配置）——网络超时会把启动卡死几十秒

### 规则 2：导出优先声明

`WEB_DIRECTORY`、`NODE_CLASS_MAPPINGS`、`NODE_DISPLAY_NAME_MAPPINGS` 必须在**任何可能失败的 import 之前**赋值。这样即使后续导入出错，ComfyUI 仍能读到这些导出，插件不会整包失联。

### 规则 3：两段式 try 保护

可能失败的基础设施导入用 try 包住，失败时**降级而非崩溃**：

```python
import os
import sys

# 1. 先把包路径与 ComfyUI 需要的导出声明完（不依赖任何第三方库）
PLUGIN_DIR = os.path.dirname(os.path.abspath(__file__))
if PLUGIN_DIR not in sys.path:
    sys.path.insert(0, PLUGIN_DIR)

WEB_DIRECTORY = "./前端"
NODE_CLASS_MAPPINGS = {}
NODE_DISPLAY_NAME_MAPPINGS = {}

# 2. 再导入自己的基础设施，失败则回退到标准库，保证上面的导出依然有效
try:
    from 后端.日志配置 import 初始化日志系统, 获取日志器

    初始化日志系统()
    logger = 获取日志器("启动")
except Exception as _e:
    import logging

    logger = logging.getLogger("插件名.启动")
    logger.exception(f"日志系统初始化失败，回退标准 logging: {_e}")

# 3. 业务模块导入同样兜住异常，失败只影响该模块，不影响整包加载
try:
    from 后端 import 接口路由  # noqa: F401  导入即注册路由

    logger.info("后端接口路由加载成功")
except Exception as e:
    logger.exception(f"后端加载失败: {e}")

__all__ = ["WEB_DIRECTORY", "NODE_CLASS_MAPPINGS", "NODE_DISPLAY_NAME_MAPPINGS"]
```

> 关键顺序：**路径 → 导出 → 基础设施 → 业务模块**。每一层失败都不影响上一层已完成的工作。

### 规则 4：副作用后置

数据迁移、索引预热、缓存构建这类一次性工作，不要在导入期同步执行。三种后置方式：

- **首次请求触发**：路由内用 `if not _已初始化:` 惰性初始化
- **后台任务**：`loop.create_task(...)` 交给事件循环，导入立即返回
- **显式入口**：让用户在面板上主动点一次「初始化 / 重建索引」

## 四、延迟导入（lazy import）

### 三种写法

```python
# 写法 1：函数内导入——最常用，重依赖只在真正用到时才加载
def 生成缩略图(image):
    import cv2  # 只有调用这个函数才付出 cv2 的导入代价
    ...


# 写法 2：模块级 __getattr__（PEP 562）——对外仍是模块属性，内部按需加载
def __getattr__(name):
    if name == "重型工具":
        from . import 重型工具 as m
        return m
    raise AttributeError(name)


# 写法 3：仅为类型标注的导入——运行时完全不导入
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    import torch  # 只给类型检查器看
```

### 何时该延迟、何时不该

| 情况 | 处理 |
|---|---|
| 依赖体积大 / 导入慢（`cumulative` 排前列） | 延迟 |
| 只有少数代码路径用到 | 延迟 |
| 可能未安装（可选功能） | 延迟 + try 兜底 |
| 轻量且几乎所有路径都用（os / json / 自己的常量模块） | 保持顶层 |

反例：为了「统一风格」把所有 import 都塞进函数内。每次调用都要走一次模块查表，可读性也变差，属于过度优化——**只对测出来重的依赖做延迟**。

## 五、依赖治理

### requirements.txt 只写「真实用到且宿主没带」的

ComfyUI 宿主环境已经带了 torch、torchvision、numpy、Pillow、aiohttp 等。这些**不要写进 requirements.txt**，更不能钉版本——插件的一句 `torch==2.1.0` 可能触发 pip 重装 torch，直接破坏用户整个 ComfyUI 环境。

版本约束原则：

- 用下界或兼容区间：`requests>=2.31`、`pydantic~=2.6`
- 只在确实存在已知不兼容时才写上界：`numpy>=1.24,<2.0`
- 禁止 `==` 精确锁死（除非该包有明确的破坏性变更历史且你已验证）

### 可选依赖用统一降级模式

```python
try:
    import 某可选库
except ImportError:
    某可选库 = None


def 高级功能(...):
    if 某可选库 is None:
        raise RuntimeError("此功能需要安装 某可选库：pip install 某可选库")
    ...
```

要点：顶层不硬 import；提示信息里给出**可直接复制的安装命令**；核心功能在缺少可选依赖时仍然可用。

### 清理僵尸依赖

- `ruff check`（或 `pyflakes`）抓未使用的导入（F401）
- 逐条 grep 确认 requirements.txt 的每一项在代码里都有实际引用；删掉只在历史版本用过的包

## 六、不阻塞事件循环

ComfyUI 的自定义路由跑在 aiohttp 的事件循环上，**任何同步阻塞都会卡住整个 ComfyUI 的 Web 服务**（不只是你的插件面板）。

### 场景与对策

| 场景 | 症状 | 对策 |
|---|---|---|
| 同步文件读写 / 目录扫描 | 接口偶发卡顿 | `await asyncio.to_thread(fn, ...)` |
| `requests` 同步请求 | 面板整体假死数秒 | 换 `aiohttp`；无法改造时用 `to_thread` 兜底 |
| 子进程、语法检查、打包压缩 | 秒级卡顿 | `loop.run_in_executor(None, fn, ...)` |
| 大 JSON 序列化 / 索引构建 | 首次访问卡顿 | 后台任务 + 结果缓存，别放在请求路径上 |
| 模型加载 | 首次执行长时间无响应 | 延迟加载 + 单例复用 + 进度反馈 |

### 标准写法

```python
import asyncio


async def 处理请求(request):
    # 同步的文件读写、目录扫描一律丢进线程，避免阻塞事件循环
    数据 = await asyncio.to_thread(读取并解析文件, 路径)
    return web.json_response(数据)
```

### 三个注意点

- **`to_thread` 不解决 CPU 密集**：受 GIL 限制，纯计算放线程里照样占满一个核并拖慢主线程。真正的 CPU 密集任务用 `ProcessPoolExecutor`，或干脆放到节点执行期（ComfyUI 的执行本身在独立流程里）。
- **async 函数内禁止 `time.sleep`**：需要等待用 `await asyncio.sleep(...)`。
- **节点 `execute` 内不要 `asyncio.run`**：当前线程已有运行中的事件循环时会抛 `RuntimeError: asyncio.run() cannot be called from a running event loop`。需要复用现有循环（`get_event_loop().create_task`），或直接写同步实现。

## 七、检查清单

- [ ] `python -X importtime` 测过导入耗时，且 < 200ms（或已说明为何无法更低）
- [ ] `__init__.py` 顶层无重依赖、无模型加载、无网络请求、无磁盘递归扫描
- [ ] `WEB_DIRECTORY` / `NODE_CLASS_MAPPINGS` / `NODE_DISPLAY_NAME_MAPPINGS` 在所有可能失败的 import 之前赋值
- [ ] 基础设施导入有 try 兜底与降级路径，业务模块导入失败不影响整包
- [ ] 迁移 / 预热 / 索引构建已后置（首次请求、后台任务或显式入口）
- [ ] 重依赖已改为延迟导入，且未把所有 import 都塞进函数内
- [ ] requirements.txt 无宿主自带包、无 `==` 锁死、无僵尸依赖
- [ ] 可选依赖走 try + 降级，提示里带安装命令
- [ ] 所有同步 IO / 子进程调用已用 `to_thread` 或 `run_in_executor` 移出事件循环
- [ ] 节点内没有 `asyncio.run`，async 函数内没有 `time.sleep`

## 八、常见踩坑

| 坑 | 规避 |
|---|---|
| 顶层 import 重依赖，ComfyUI 整体启动变慢 | 用 `-X importtime` 定位后改延迟导入 |
| 导入期一个异常导致整个插件包不加载、节点消失 | 两段式 try + 导出优先声明 |
| requirements 钉死 torch/numpy 版本，pip 重装破坏用户环境 | 宿主自带依赖一律不声明 |
| 导入期检查更新，网络不通时启动卡死几十秒 | 网络请求一律后置且带超时 |
| async 路由里直接做同步文件读写 | `await asyncio.to_thread(...)` |
| 以为 `to_thread` 能加速 CPU 密集任务 | GIL 限制，改用进程池或移到节点执行期 |
| 节点内 `asyncio.run` 报 running event loop | 复用当前循环或改同步实现 |
